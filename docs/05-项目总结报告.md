# 安心诊聊平台（AXZL）项目总结报告

## 1 项目概述

### 1.1 项目背景

随着"互联网+医疗健康"政策的深入推进和人工智能技术的快速发展，传统医疗服务模式正在经历深刻变革。本项目提出建设"安心诊聊平台"（AXZL），利用大语言模型（LLM）和检索增强生成（RAG）技术，构建一个集智能问诊、健康档案管理、用药提醒于一体的医疗健康服务平台，旨在为用户提供便捷、专业、个性化的健康咨询服务。

### 1.2 项目目标

本项目的核心目标包括：

1. 基于RAG技术实现智能问诊功能，结合医学知识库和用户健康档案提供个性化AI健康咨询
2. 构建文档处理流水线，支持多格式文档的上传、解析、分块和向量化
3. 建立个人健康档案管理，作为问诊上下文自动注入AI对话
4. 实现用药提醒功能，帮助用户管理日常用药计划
5. 实现基于RBAC的多角色权限管理体系
6. 支持多种AI大模型的动态配置和热切换

### 1.3 开发周期

| 阶段 | 时间 | 主要工作 |
|------|------|---------|
| 需求分析 | 第1-2周 | 需求调研、功能规划、技术选型 |

| 部署上线 | 第15-16周 | 环境部署、文档编写、项目验收 |

### 2.2 系统架构

系统采用Maven多模块架构，共包含5个模块：

```
axzl-admin    → Web入口层（Controller、启动配置）
axzl-biz      → 业务逻辑层（AI问诊、知识库、健康档案）
```

模块依赖关系清晰：admin → framework → system → common，admin → biz → common。

### 2.3 核心技术实现

#### 2.3.1 RAG智能问诊流程

本系统的核心技术是基于RAG（Retrieval-Augmented Generation）的智能问诊流程：

```
用户输入 → 文本向量化(BGE) → Milvus向量检索(Top-5) → 健康档案注入 → Prompt组装 → LLM调用 → 流式响应
```

**关键技术点：**

1. **向量检索**：使用BGE-large-zh-v1.5模型将用户输入和知识库文本向量化，存储在Milvus中，通过余弦相似度进行Top-5检索，阈值设为0.6。
2. **健康档案上下文注入**：自动加载用户的性别、年龄、血型、过敏史、既往病史、家族病史等信息，作为Prompt的一部分注入AI对话上下文，实现个性化问诊。
3. **SSE流式响应**：使用SseEmitter + Flux实现服务端向客户端的流式数据推送，支持逐token实时显示AI回复。采用后台订阅者模式，即使前端断开连接，AI回复仍能完整持久化。
4. **对话历史管理**：每次对话自动保存用户消息和AI回复，AI回复同时记录向量检索结果（JSON格式），支持追溯和分析。

#### 2.3.2 文档处理流水线

系统实现了异步文档处理流水线：

```
文档上传 → @Async异步处理 → 文本提取(CustomDocumentReader) → 分块策略 → 批量向量化(20条/批) → 双写(Milvus + MySQL)
```

**分块策略：**
- 文档<3000字符：整体存储，不做分块
- 文档≥3000字符：按段落分块，每块800字符，块间50字符重叠

**支持格式：** txt、Word（docx）、PDF、Markdown、JSONL

#### 2.3.3 动态AI模型管理

系统支持通过数据库动态配置AI模型，无需修改代码和重启：

- `biz_ai_model_config`表存储模型配置（提供商、API地址、密钥、参数等）
- `SpringAIClientFactory`工厂类管理ChatClient和EmbeddingModel实例
- 使用ConcurrentHashMap缓存客户端实例，支持`refreshCache()`动态刷新
- 所有模型通过OpenAI兼容接口统一调用，通过`api_base_url`区分不同Provider
- 支持一键切换默认模型，立即生效

#### 2.3.4 安全认证体系

系统采用无状态JWT认证体系：

- HS512算法签名，有效期30分钟
- Redis存储登录会话，支持分布式部署
- 令牌剩余<20分钟自动刷新
- BCrypt密码加密，连续5次失败锁定10分钟
- XSS过滤、防重复提交、接口限流等多层安全机制

#### 2.3.5 双布局前端架构

前端采用双布局架构：

- **管理端布局**：侧边栏 + 顶部导航 + 面包屑，基于RuoYi框架风格
- **患者端布局**：顶部标题栏 + 底部Tab导航，适配移动端风格
- **动态路由**：根据用户权限从后端`/getRouters`接口获取菜单，前端动态生成路由

## 4 创新点与特色

### 4.1 RAG + 健康档案的个性化问诊

本系统的核心创新在于将RAG技术与用户健康档案相结合，实现个性化的AI问诊：

- 传统AI问诊仅基于通用知识回复，缺乏对用户个体差异的考虑
- 本系统在问诊时自动注入用户的过敏史、既往病史、家族病史等个人健康信息
- AI回复能够体现用户的个人特征，如"您有青霉素过敏史，请避免使用青霉素类药物"
- 结合知识库的医学文献检索，提供有据可依的专业建议

### 4.2 动态AI模型热切换

系统支持通过数据库动态配置和切换AI模型，无需修改代码和重启：

- 预置DeepSeek、OpenAI、Anthropic等多种模型配置
- 每个模型类型可设置一个默认模型，切换后立即生效
- 使用客户端工厂模式和ConcurrentHashMap缓存，性能优异
- 支持通过OpenAI兼容接口统一调用不同Provider的模型

### 4.3 异步文档处理与向量化

系统实现了完整的文档处理流水线：

- 支持txt、Word、PDF、Markdown、JSONL等多种格式
- 采用@Async异步处理，不阻塞用户请求
- 智能分块策略：小文档整体存储，大文档按段落分块
- 批量向量化（20条/批），高效处理大量文档
- 处理状态实时可查，失败支持重试

### 4.4 SSE流式对话与后台持久化

系统采用SSE（Server-Sent Events）实现流式AI对话：

- 用户体验：AI回复逐token实时显示，首字响应快
- 数据完整性：采用后台订阅者模式，即使前端断开连接，AI回复仍能完整持久化
- 会话元数据：自动更新消息数量、Token消耗、症状摘要等

### 4.5 双布局前端架构

系统前端采用双布局架构，管理端和患者端使用不同的界面风格：

- 管理端：传统后台管理风格，侧边栏导航，功能全面
- 患者端：简洁的移动端风格，底部Tab导航，操作便捷
- 动态路由：根据用户权限动态加载菜单，无权限的菜单不显示

### 4.6 多角色精细化权限控制

系统实现了5种角色的精细化权限控制：

- 超级管理员：所有功能权限
- 医疗专家：知识库管理、文档管理、问诊管理
- 普通医生：智能问诊、知识库查询、健康档案管理
- 护士助理：问诊查询、档案查询
- 患者：智能问诊、健康档案管理、用药提醒

权限控制精确到按钮级别，权限标识格式为`模块:子模块:操作`。

## 5 遇到的问题与解决方案

### 5.1 SSE流式对话数据丢失问题

**问题描述：** 在SSE流式对话中，当前端用户提前关闭页面或网络断开时，AI回复的数据会丢失，导致对话记录不完整。

**解决方案：** 采用后台订阅者模式。Flux的subscribe方法中，onNext回调负责向前端推送数据（捕获IOException），onComplete回调负责将完整回复保存到数据库。即使前端断开，后台订阅者继续接收AI回复并持久化。

### 5.2 大文档上传内存溢出问题

**问题描述：** 上传较大的文档（如10MB的PDF）时，文本提取过程导致内存溢出。

**解决方案：**
1. 限制单文件上传大小为10MB
2. PDF解析采用PDFBox的流式解析模式，避免一次性加载全部内容
3. 文本提取后立即释放原始文件资源
4. 分块处理时采用逐块处理而非全部加载到内存

### 5.3 AI模型切换缓存不一致问题

**问题描述：** 在管理界面切换默认AI模型后，系统仍使用旧模型进行问诊。

**解决方案：** 实现`SpringAIClientFactory.refreshCache()`方法，清除ConcurrentHashMap中的客户端缓存。切换默认模型时调用该方法，下次问诊时自动创建新的客户端实例。

### 5.4 向量化批量处理性能问题

**问题描述：** 批量向量化大量文本时，逐条调用EmbeddingModel导致性能低下。

**解决方案：** 实现批量向量化，每批处理20条文本。EmbeddingModel支持批量输入，单次调用可处理多条文本，大幅提升了向量化效率。

### 5.5 前端动态路由权限问题

**问题描述：** 用户登录后，动态路由未正确加载，导致部分页面404。

**解决方案：**
1. 在路由守卫（beforeEach）中检查权限路由是否已加载
2. 未加载时调用`/getRouters`接口获取菜单数据
3. 使用`filterAsyncRoutes`将后端菜单数据转换为Vue Router路由配置
4. 使用`router.addRoute`动态添加路由
5. 添加`replace: true`避免路由历史堆栈问题

### 5.6 中文文档解析乱码问题

**问题描述：** 部分中文文档上传后，文本提取出现乱码。

**解决方案：**
1. 统一使用UTF-8编码处理所有文本
2. Excel导入导出时显式指定编码格式
3. PDF解析时使用PDFBox的文本提取器，自动处理编码
4. 数据库连接配置UTF-8字符集（utf8mb4）

## 6 不足与改进方向

### 6.1 当前不足

1. **AI回复质量**：受限于大语言模型的能力，AI回复可能存在不准确或"幻觉"现象，需要更强的医学领域微调模型。
2. **知识库规模**：当前知识库规模有限，需要持续扩充医学知识数据以提高检索质量。
3. **多模态支持**：目前仅支持文本问诊，不支持图片（如医学影像）和语音输入。
4. **实时性**：AI问诊依赖外部API调用，受网络和服务商影响，响应时间可能波动。
5. **移动端适配**：患者端虽有独立布局，但未开发原生移动应用，部分交互体验不如原生App。

### 6.2 未来改进方向

1. **医学领域模型微调**：使用医疗问答数据对大语言模型进行微调，提高医学回复的准确性和专业性。
2. **知识库持续扩充**：接入更多权威医学知识源，如临床指南、医学教科书、药品说明书等。
3. **多模态问诊**：支持医学影像（X光、CT等）的AI辅助解读，支持语音输入和语音回复。
4. **移动端App**：开发基于uni-app或Flutter的移动端应用，提供更好的移动体验。
5. **智能分诊**：基于用户描述的症状，智能推荐就诊科室和医生。
6. **用药提醒增强**：支持药物相互作用检查、用药提醒推送通知、与健康档案联动等功能。
7. **健康数据分析**：基于用户的健康档案和问诊记录，生成健康趋势报告和风险评估。
8. **分布式部署**：优化系统架构，支持微服务化部署，提高系统可扩展性和可用性。

## 7 开发经验总结

### 7.1 技术经验

1. **Spring AI框架**：Spring AI提供了统一的AI模型调用抽象，通过OpenAI兼容接口可以统一调用不同Provider的模型，降低了多模型集成的复杂度。
2. **RAG架构设计**：RAG流程中，Prompt的设计对AI回复质量影响很大。需要精心设计Prompt模板，合理组织知识库检索结果、用户档案和对话历史的注入顺序和格式。
3. **SSE流式通信**：SSE是实现AI流式对话的良好方案，相比WebSocket更简单，但需要注意前端断开连接后的数据持久化问题。
4. **向量数据库选型**：Milvus作为开源向量数据库，支持多种索引类型和距离度量，性能优异。IVF_FLAT索引在数据量适中时表现良好。
5. **多模块架构**：Maven多模块架构有助于代码组织和依赖管理，但需要注意模块间的依赖方向，避免循环依赖。

### 7.2 项目管理经验

1. **需求管理**：在项目初期充分调研需求，明确功能边界和优先级，避免开发过程中的需求变更。
2. **迭代开发**：采用迭代式开发，先实现核心功能（智能问诊），再逐步扩展其他模块（知识库、健康档案、用药提醒）。
3. **代码规范**：遵循阿里巴巴Java开发规范，使用统一的代码风格和命名规范，提高代码可读性和可维护性。
4. **文档先行**：在编码前完成系统设计文档，明确接口定义和数据模型，减少开发过程中的返工。
5. **持续测试**：在开发过程中持续进行单元测试和集成测试，及时发现和修复Bug。

### 7.3 团队协作经验
